# Working in this repository

Workspace for MemoMind smart-glasses apps. Read
[`docs/glasses-platform.md`](docs/glasses-platform.md) before writing plugin
code — it covers the hardware envelope, the memory budgets, and the lifecycle
contract, and maps questions to the SDK's own docs.

## Setup and builds

The SDK is not vendored. If `.sdk/` is missing, run `./mm setup` (fetches the
commit pinned in `sdk.lock`, then downloads the RISC-V toolchain — slow the
first time, cached afterwards).

Always build through `./mm build`, never by invoking the SDK's `build.py`
directly. `./mm` keeps output in `build/` and keeps plugin sources out of the
SDK tree.

```sh
./mm doctor           # environment check; run this first when a build misbehaves
./mm build            # everything
./mm build hello_hud  # one plugin
./mm test             # host-side test suites
./mm sim star_finder  # render a glasses plugin's screens on this machine
```

A glasses build prints its real budget usage — read it, it is the fastest
signal that a change is getting expensive:

```
packed XIP ...: Flash=1036/512000 B; static RAM=32 B
plugin stack: maximum function frame 144/1024 B
```

## Writing glasses plugins (`plugins/glass/`)

Compiled with `-Wall -Wextra -Werror -std=gnu99`, freestanding, no libc linked.
Match the surrounding style: 4-space indent, `0` rather than `NULL`, `(void)x`
for unused parameters.

Rules that the compiler will not catch for you:

- **Never allocate in `gm_plugin_entry`.** A rejected descriptor has no
  callback that could free it. Acquire in `on_load`, create UI in `on_start`.
- **A failed `on_start` never gets `on_stop`** — it must clean up its own
  partial UI. A failed `on_load` *does* get `on_unload`, which must therefore
  tolerate a half-initialized context.
- **Never block, sleep, or spin** in a callback. They run serialized on the
  display task, sharing an 8 KiB stack with the firmware.
- **Never nest rendering paths.** No LVGL call while a framebuffer slice is
  locked — it can deadlock the display task.
- **Never retain a borrowed pointer.** BT payloads in `on_event` are valid only
  until the callback returns; copy what you need.
- **Validate before use.** Check `struct_size`, `abi_version`, capability bits,
  and every function pointer you intend to call. Resolve extensions with
  `extension_get` and handle `GM_PLUGIN_ENOTSUP`.
- **Watch where bytes live.** `static const` stays in Flash; a mutable global
  spends the < 100 KiB static RAM budget for the plugin's whole lifetime; a
  large local fails the 1024 B per-frame check. Big buffers use
  `host->alloc()`/`free()` with failure handling.
- **Never hard-code 600 x 350.** Call `host->display_get_info()`.

## Writing web plugins (`plugins/web/`)

Every Bridge method needs its permission declared in `manifest.json` — see
`.sdk/PhoneSDK/docs/web-plugin/capability-contract.md` for the exact mapping.

`vendor/gm-plugin-web-sdk.esm.js` is generated by `./mm build` and git-ignored.
Do not commit it or edit it by hand.

## Testing without hardware

There is no glasses simulator on Linux, so logic that can be checked on the
host is worth extracting so that it can be. `plugins/glass/star_finder`
follows this: the tracking math lives in its own `orientation.c`, which
`tests/orientation_test.c` compiles natively and drives with synthetic input.
Prefer that shape over burying non-trivial math inside a lifecycle callback.

Declare new suites in `tests/tests.json` (`kind: "c"` or `kind: "node"`)
rather than adding another runner. Keep test sources outside
`plugins/glass/*/`, because the SDK build compiles every `.c` it finds in a
plugin directory.

Assert invariants over golden numbers where you can. The astronomy suite
checks sidereal time at a known epoch, Polaris tracking latitude, and
meridian transits landing due north or south — all of which stay meaningful
without a reference ephemeris to diff against.

`./mm sim <plugin>` renders a glasses plugin's screens by compiling it
natively against a mock Host (`tools/simstudio/`). Use it to see a UI change
and to catch lifecycle violations — it fails the run if objects survive
`on_stop`. Read `tools/simstudio/README.md` for its limits before trusting a
frame: text metrics are DejaVu, not the firmware font, and nothing about the
RV32 ABI or hardware is exercised. Never describe a simstudio frame as the
app running on the glasses.

## Before claiming something works

`./mm build` and `./mm test` must both pass. MemoMind publishes no Linux build
of Desktop Studio (`.sdk/Studio/linux/` holds only a `.gitkeep`, and the
repository has no releases), so a clean build, passing tests and a simstudio
frame are the strongest local signals — say so plainly rather than implying
the app was seen running on a device.

## Copy before inventing

The SDK ships worked examples for nearly every subsystem under
`.sdk/GlassSDK/examples/` and `.sdk/PhoneSDK/examples/`. Read the nearest one
first; `examples/README.md` in each maps example to capability.
